EqOne — Micro-Frontend Architecture Proposal

Category-aligned micro-frontends for the EqOne platform (one.equiniti.com)
Solution Architecture proposal · for architecture & leadership review · Draft v1.0

Executive summary

EqOne is proposed to move from a single application to a set of micro-frontends (MFEs) grouped by business category, rather than one per individual product. A Shell owns the common platform (sign-in, identity, holdings and cross-cutting controls); four category MFEs — Shares Reg, All-Employee Plans, Discretionary and a proposed Shared EFSL (to be confirmed) — are each owned by one team and paired with their own Experience API.

To the customer it remains one EqOne application with a single sign-in. Each team gains independent delivery, the estate scales cleanly to more products, and rollout is gated and reversible. The model is deliberately coarse-grained for Q3, with the option to split further later as teams and products mature.

Naming. The application is EqOne (one.equiniti.com). Existing repository and project names — EQNexusUI (the current UI) and Equiniti.Nexus.Experience.Api (the current Experience API) — are retained as-is.

Why group by category rather than by product

  • Boundaries follow teams. Each MFE is owned by one team, so it can be built, tested and deployed independently — the core benefit of micro-frontends.
  • Fewer moving parts. Grouping related products keeps the estate to five MFEs rather than one per product, reducing repositories, pipelines and coordination.
  • Change cohesion. Products in the same category tend to change together and share models and components, so related work stays in one place.
  • Coarse now, split later. Categories can be split into finer MFEs when a product and an independent team justify it — avoiding premature fragmentation.

3 · Cross-cutting controls

The Shell owns the cross-cutting platform controls — authentication, IDV, fraud and impersonation. These are exposed through Module Federation and inherited automatically by every MFE through the shared EqOne session. The category MFEs do not re-implement or separately wire these controls; they consume them from the Shell by default.

Net effect: sign-in and the regulatory controls are built once in the Shell and apply consistently across every MFE — there is no duplication and no risk of a product drifting from the platform's security behaviour.

4 · Experience API model

Each MFE is paired with its own Experience API, so a team owns its user experience end to end — front-end and back-end-for-frontend together.

  • The Shell continues to use the existing Equiniti.Nexus.Experience.Api.
  • Four new Experience APIs are created — one per category MFE (Shares Reg, All-Employee, Discretionary, Shared EFSL *).
  • Common back-end concerns — session validation, GIP service token, resilience and shared models — live in a shared library consumed by all five, so they are implemented once.
Figure 3 — Each MFE is paired with its own Experience API; the Shell keeps the existing API. Common back-end concerns are provided once through a shared library, and all APIs read their own backend systems plus Common Services and Umbraco.

7 · Security

One sign-in, one session, controls owned once by the Shell.

Figure 7 — Security flow. The customer signs in once at GIP; the Shell owns the session and shares it silently with every MFE; each MFE calls its Experience API with a Bearer JWT, which is validated before any work; downstream calls use a GIP service token. IDV, fraud and impersonation are owned by the Shell.
  • Single sign-in via GIP (Azure B2C). The Shell owns the session and shares it silently with every MFE — customers never log in per product.
  • Token validation: every MFE → Experience API call carries a Bearer JWT; the Experience API validates issuer, audience and signature before doing any work. (Inbound validation to be hardened before production.)
  • Downstream auth: calls to backend systems (Sirius, Centive, Xanite, tOption) use a GIP service token (client-credentials), never the user token. Secrets are held in AWS Secrets Manager, never in the repository.
  • Regulatory controls — IDV, fraud and impersonation — are owned by the Shell and inherited by every MFE, so they behave identically everywhere.
  • Data: no personal data in feature flags or telemetry; HTTPS throughout; least-privilege per service.

11.2 · Cost

The split (5 ECS services, 5 pipelines, S3, CloudFront) costs more to run than a single SPA — but the cost is proportional to teams and products, and it buys independent delivery. We keep it in check as follows:

Cost driverNoteControl
ECS services (5)one per APIRight-size tasks; autoscale; consolidate low-traffic APIs if needed.
Pipelinesone per repoOne shared pipeline template; ephemeral build agents.
S3 + CloudFrontone bucket, one distributionFolders (not buckets); cache hashed assets for a long TTL.
Observabilitylog / trace volumeSampling and a retention policy.
Starting coarse (five APIs, not one-per-product) keeps the running cost down; we only add services when a split is justified.

13 · Migration & delivery

How we get from today's single-page application to the category-MFE model without blocking the MVP.

Figure 11 — Migration. All work is additive and flag-gated on one trunk, so the MVP keeps shipping throughout; products are enabled one at a time behind a flag.
  • Phase 0 (weeks 0–2): stand up the Shell as the Module Federation host on the existing EQNexusUI repo; create the shared library, a pipeline template and a first Experience API skeleton. Flags off.
  • Phase 1: deliver the first category MFE (e.g. All-Employee / SAYE) end to end behind a flag — proving the golden path (build → deploy → run → observe).
  • Phase 2: roll out the remaining MFEs one at a time behind flags; migrate Shares Reg by lifting existing code, not rewriting it.
  • Phase 3: retire flags as features stabilise; split a category into finer MFEs only when justified.
Rollback & MVP safety: flags off restore today's behaviour instantly, per product; the MVP is untouched throughout. There is no big-bang cutover and no long-lived branch.

14 · Benefits

  • Team independence. Each team owns one MFE and its Experience API and can release without waiting on others.
  • Scales cleanly. New products join an existing category, or a new category MFE is added — without touching the others.
  • Consistent, seamless customer experience. One EqOne application, one sign-in, one design system.
  • Safe, reversible rollout. Each MFE is enabled behind a runtime flag; any issue is isolated to one area and reversible instantly.
  • MVP protected. Work is additive and flag-gated, so the current EqOne application keeps shipping throughout.
  • Right-sized for now. Coarse categories for Q3, with the option to split further as products and teams grow.
